## The Distributed Consistency Problem

In monolithic systems, you can update multiple tables (e.g., `orders` and `inventory`) inside a single database transaction. If anything fails, the database rolls back everything, ensuring consistency:

```sql
BEGIN TRANSACTION;
UPDATE orders SET status = 'completed' WHERE id = 123;
UPDATE inventory SET stock = stock - 1 WHERE item_id = 999;
-- If any query fails, rollback; otherwise commit.
COMMIT;
```

In **microservices**, the Order Service has its own database, and the Inventory Service has its own database. You cannot use database-level ACID transactions across a network partition. If you update the order database and the network cuts out before updating the inventory database, your system is left in an **inconsistent state**.

## The Transactional Outbox Pattern

A common way microservices stay in sync is by publishing events (e.g., Order Service publishes `OrderCreated` to a Message Queue, and Inventory Service consumes it).

### The Dual-Write Problem
What happens if you update your database, and then publish to the message broker?
1. Write to DB succeeds.
2. The Message Queue server is down.
3. The event is never sent. The databases are now permanently out of sync.

### How the Outbox Pattern Solves It
1. Create an `outbox` table inside the **same database** as your business tables.
2. When you perform a write operation, save both the business entity (e.g., the new Order) and the event details (e.g., `OrderCreatedEvent`) into the `outbox` table in a **single local database transaction** (atomic, 100% reliable).
3. A separate background process (called an **Outbox Publisher** or Message Relayer) polls the `outbox` table, reads unsent events, publishes them to the Message Queue, and deletes/marks them as sent.

```text
[Order Service] 
    |
    v (Atomic Local Transaction)
[SQL DB] ---> [orders table]
         ---> [outbox table]
                  |
                  v (Polls and Publishes)
            [Outbox Publisher (Worker)] ---> [Message Queue (RabbitMQ/Kafka)]
```

## The Saga Pattern

To coordinate multi-service business transactions (e.g., booking a vacation with Flight, Hotel, and Payment), we use the **Saga Pattern**.

A Saga is a sequence of local transactions. Each local transaction updates the database and publishes an event. If a step fails, the Saga runs **Compensating Transactions** (rollback operations) in reverse order to undo the changes.

### 1. Choreography (Decentralized)
Services listen to events and trigger their own local transactions without a central controller.
* **Pros**: Simple for simple workflows; low coupling.
* **Cons**: Hard to debug or track the state of complex transactions.

### 2. Orchestration (Centralized)
A central service (an Orchestrator) controls the sequence, sends commands to participants, and coordinates rollbacks if failures occur.
* **Pros**: Highly visible state; easy to manage complex logic.
* **Cons**: The Orchestrator can become a Single Point of Failure (SPOF) or bottle up business logic.

## Idempotency Keys

In distributed systems, networks are unreliable. A client might send a payment request, but the connection cuts out while waiting for a response. The client retries. If your API is not **idempotent**, the user gets charged twice.

An **Idempotency Key** is a unique identifier (usually a UUID) generated by the client and sent in the header of a request.
* **First Request**: Server checks if the key exists in its database/cache. It doesn't. Server processes the request, saves the response under the key in Redis (with a TTL), and returns the response.
* **Retry Request**: Server checks the key. It exists. Server immediately returns the cached response without running the payment logic again.

## JavaScript Implementation Examples

### 1. Transactional Outbox Pattern in Node.js
Here is how you write to an outbox within a PostgreSQL transaction:

```javascript
// npm install pg
const { Pool } = require('pg');
const pool = new Pool();

async function createOrder(userId, items) {
  const client = await pool.connect();

  try {
    await client.query('BEGIN'); // Start transaction

    // 1. Create order
    const orderQuery = 'INSERT INTO orders(user_id, status) VALUES($1, $2) RETURNING id';
    const orderRes = await client.query(orderQuery, [userId, 'PENDING']);
    const orderId = orderRes.rows[0].id;

    // 2. Write event to outbox table
    const eventPayload = { orderId, userId, items };
    const outboxQuery = 'INSERT INTO outbox(event_type, payload, status) VALUES($1, $2, $3)';
    await client.query(outboxQuery, ['OrderCreated', JSON.stringify(eventPayload), 'PENDING']);

    await client.query('COMMIT'); // Commit both atomically
    console.log('Order created and event written to outbox!');
  } catch (error) {
    await client.query('ROLLBACK'); // Roll back both if either fails
    console.error('Order creation failed, rolling back:', error);
  } finally {
    client.release();
  }
}
```

### 2. Idempotency Key Middleware
Here is an Express middleware using Redis to handle idempotent endpoints:

```javascript
// npm install express ioredis
const express = require('express');
const Redis = require('ioredis');

const app = express();
const redis = new Redis();

app.use(express.json());

async function idempotencyMiddleware(req, res, next) {
  const idempotencyKey = req.headers['idempotency-key'];

  if (!idempotencyKey) {
    return res.status(400).json({ error: 'Idempotency-Key header is missing' });
  }

  const redisKey = `idempotency:${idempotencyKey}`;

  try {
    // Attempt to set key only if it doesn't exist (NX) with a 24-hour expiration (EX 86400)
    // Set value as "PROCESSING" initially
    const lockAcquired = await redis.set(redisKey, 'PROCESSING', 'EX', 86400, 'NX');

    if (!lockAcquired) {
      // Key exists. Fetch current state.
      const val = await redis.get(redisKey);
      if (val === 'PROCESSING') {
        return res.status(409).json({ error: 'Duplicate request already in progress' });
      } else {
        // Return the cached response
        const cachedResponse = JSON.parse(val);
        return res.status(cachedResponse.status).json(cachedResponse.body);
      }
    }

    // Attach key to request so the handler can save the final response
    req.idempotencyKey = redisKey;
    next();
  } catch (err) {
    console.error('Idempotency error:', err);
    next(); // Fall-open
  }
}

// Router route using middleware
app.post('/api/payments', idempotencyMiddleware, async (req, res) => {
  try {
    // Perform payment processing logic...
    const paymentResult = { transactionId: 'tx_98765', status: 'SUCCESS' };
    
    // Save final response payload in Redis
    const responsePayload = { status: 200, body: paymentResult };
    await redis.set(req.idempotencyKey, JSON.stringify(responsePayload), 'EX', 86400);

    res.status(200).json(paymentResult);
  } catch (err) {
    // If process failed, clear lock so user can try again
    await redis.del(req.idempotencyKey);
    res.status(500).json({ error: 'Payment processing failed' });
  }
});
```

## 2-Phase Commit (2PC) vs. Sagas

When designing consistency across distributed databases, you will often compare **Two-Phase Commit (2PC)** and **Sagas**.

### 1. Two-Phase Commit (2PC)
A classic database protocol that ensures distributed transactions commit atomically. It uses a central coordinator:
1. **Prepare Phase**: The coordinator asks all database nodes if they are ready to commit. Each node locks its resources and says "Yes" or "No".
2. **Commit Phase**: If all nodes say "Yes", the coordinator tells them to commit. If anyone says "No", the coordinator tells everyone to rollback.

#### Why 2PC is avoided in modern, high-scale microservices:
* **Synchronous & Blocking**: All database nodes lock their rows and wait during the network round-trips. If the coordinator crashes mid-transaction, those locks are held indefinitely, freezing the database.
* **Low Latency Tolerance**: High latency or slow networks directly degrade database lock throughput.
* **Single Point of Failure (SPOF)**: If the coordinator is offline, transactions cannot resolve.

---

### 2. Sagas (Eventual Consistency)
Instead of blocking resources, a Saga performs a series of **independent local transactions** asynchronously. 
* **Compensating Transactions**: If step 3 fails, the system executes undo operations for steps 1 and 2 in reverse order.
* **Eventual Consistency**: The system is temporarily inconsistent (e.g., flight is booked, but payment is still processing), but resolves to a consistent state once the saga completes or rolls back.

### Summary Comparison

| Feature | Two-Phase Commit (2PC) | Saga Pattern |
| :--- | :--- | :--- |
| **Consistency** | **Strong Consistency** (Instant) | **Eventual Consistency** (Delayed) |
| **Locking** | Yes (synchronous blocking locks on DB rows) | No (databases execute local commits immediately) |
| **Scalability** | Low (degrades with network latency/nodes) | High (fully asynchronous and non-blocking) |
| **Implementation** | Handled by database/TP monitors. | Must be coded in application logic. |
| **Rollback** | Automatic database rollback. | Manual (must write explicit compensating logic). |
